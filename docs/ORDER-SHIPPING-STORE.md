# 后台指定发货门店

## 操作流程

1. 客户照常选择收货地址、下单并支付，不需要选择发货门店。
2. 后台“订单管理”筛选“待发货”和“未分配”，点击订单行“指定门店”，选择启用门店后确认。
3. 发货前可以点击“调整门店”。订单详情记录每次分配的原门店、目标门店、操作人及时间，按时间倒序展示。
4. 在订单详情填写快递公司、物流单号，订单进入待收货。首次发货必须已指定启用门店；提交时校验门店没有被其他人员调整。
5. 发货之后不能修改门店。历史已发货但没有门店信息的订单保留原状，允许继续更新物流。

## 业务规则

- 仅已支付、未发货的配送订单允许分配；未支付、自提、已发货、已结束订单不允许分配。
- 退款、退换货处理中，禁止分配、调整门店和发货。
- 使用现有 `business:order:edit` 权限。全局运营账号可以分配未分配订单；现有 verifier 门店范围账号只可操作范围内订单和门店，未分配配送订单不会对其开放。
- 门店范围过滤按配送订单的发货门店、自提订单的自提门店分别执行；没有门店部门映射的受限账号继续看不到订单。
- 使用订单行锁串行处理分配、首次发货及状态变更，并检查前端读取的旧门店，避免覆盖他人的分配结果。
- 门店名称保存分配时快照，之后重命名不改变历史订单和分配记录；被订单或分配记录引用的门店不能直接删除。
- 门店停用后不能新分配、不能首次发货；总后台可以将未发货订单调整到其他启用门店。
- 小程序订单详情展示已分配的发货门店名称。付款和下单接口不接受客户指定发货门店。
- 商品和规格库存继续使用原来的统一库存；本次没有新增分店库存、自动调拨、拆单、多门店分包或门店结算。

## 数据库与接口

执行 `sql/business-order-shipping-store-upgrade.sql`；完整初始化迁移也包含同样结构。
迁移可重复执行，仅新增字段、索引和分配记录表，不自动给历史订单指定门店。

- `biz_order.shipping_store_id`：发货门店关联。
- `biz_order.shipping_store_name`：分配时门店名。
- `biz_order_store_assignment`：历次分配流水。
- `PUT /business/order/{id}/shipping-store`：`{storeId, expectedStoreId}`，首次分配时 `expectedStoreId` 为 null。
- `PUT /business/order/{id}/delivery`：首次发货传 `expectedShippingStoreId`；使用新的管理端操作。
- 订单列表支持 `shippingStoreId`、`storeAssignment=assigned|unassigned` 及原有条件联合筛选。
- 门店下拉使用 `/business/options/order/shippingStoreId`，返回门店名称和实际关联主键。
