# 2026-10-09 退换货与财务入库衔接

更新时间：北京时间 15:32。此前 14:54 的交付证据为历史快照；本文件记录之后的售后增量，不代表合同 13 项全部验收。

## 发现与处理

1. 新售后流程直接维护 `biz_order_aftersale` 和库存，旧退货入库报表只读 `biz_order_return_receipt`，会漏掉退货退款及换货的收货记录。现在按两种来源合并查询，新增入库来源、售后单号、售后类型三列，列表和导出均为 21 列；仅纳入实际有收货时间的售后记录。旧流水保持原数字标识，新流水用 `AS` 加售后记录 ID 区分，不改原业务编号。
2. 新售后确认收货缺少仓库凭证。新增 `receipt_reference`，前后台均必填，最长 128 字；相同数量与凭证重放返回原结果，改变凭证或数量会拒绝，库存和退款单不会重复生成。历史已收货记录保持空凭证，不伪造补写；界面标明历史未登记。
3. 后台售后列表固定最多 200 条，无法追查更早记录。现在提供总数与分页（每页最多 100），支持申请日期、会员编号、用户名/商品/订单/售后单号关键词、类型、状态；查询条件在翻页后保留，按 ID 倒序。退款已到账但定时任务尚未推进的售后，列表状态和状态筛选使用同一计算口径。
4. 浏览器实际访问发现本地独立退款/财务菜单升级遗漏，直接打开对应路由会进入不存在页面。备份后补齐本地两个菜单；巡检加入菜单结构、售后收货字段检查。线上两个菜单此前已存在。
5. 首次上线复核发现线上旧表排序规则混用，合并的操作人字段与 `sys_user.user_name` 比较触发 MySQL 1267。为跨来源凭证、请求号、操作人字段及账号关联做显式字符转换，随后再次部署。最终线上查询和导出均正常，不以首次部署成功替代接口验证。
